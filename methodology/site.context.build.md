# Methodology — site.context.build

Этот документ объясняет **КАК** SiteContext Builder принимает решения при извлечении
и нормализации бизнес-контекста из неструктурированного входа.

**ЧТО** делать — зафиксировано в `prompts/site.context.build.json`.

Methodology не дублирует prompt. Здесь раскрывается логика принятия решений по группам:
business identification, offer extraction, audience extraction, demand situation extraction,
positioning, proof, objections, conversion, content, brand, constraints, semantic identity,
inference handling, conflict handling, data gap classification.

Все правила ниже применяются для построения SiteContext v0.1, который оптимизирован
под автоматическую сборку AI-first сайта, а не как полноценная CRM или knowledge base.

---

## 1. Business identification

### Что обязательно определить

1. **entity_type** — что это за сущность в рыночном смысле.
   Примеры типа смысла (не hardcoded enum):
   - contract electronics manufacturer
   - marketing agency
   - dental clinic
   - software product
   - construction company

2. **category** — рыночная категория, в которой действует бизнес.
   Это не entity_type дословно, а более узкая специализация или industry domain.

3. **summary** — 1–3 предложения о том, что это за бизнес, без рекламной воды.
   Это нормализованное описание для AI downstream, не презентационный копирайтинг.

### Когда name = null

Если официальное название неизвестно — оставь `business.name = null`.
Не придумывай название из entity_type или category.

### geography[]

Если во входе упомянуты страны, города, регионы — нормализуй их как массив строк.
Если география не указана — пустой массив `[]`.

### Как выбрать entity_type vs category

`entity_type` отвечает на вопрос **что это**.
`category` отвечает на вопрос **в какой области/сегменте**.

Пример:
```json
{
  "entity_type": "contract manufacturer",
  "category": "SMD PCB assembly"
}
```

Не дублируй одно и то же значение в оба поля.

Если `entity_type`, `category` или достаточное описание бизнеса не известны,
используй `null`, а не пустую строку и не generic-формулировку. Каждый
существенный пропуск отмечай в `data_gaps[]`. Не называй бизнес по имени offer:
`semantic_identity.primary_entity` равен `business.name`, иначе
`business.entity_type`, иначе `null`.

## 2. Offer extraction

### Offer = то, что реально продаётся

Offer — это то, что компания реально может предложить/продать/оказать клиенту.
Не путай:
- **feature** (свойство продукта) — не отдельный offer.
- **capability** (возможность компании) — не отдельный offer.
- **technology** (используемая технология) — не отдельный offer.
- **proof** (доказательство) — не отдельный offer.

Если input говорит «мы делаем монтаж SMD и монтаж THT» — это два разных offer
только если они действительно продаются раздельно.

Если input говорит «у нас есть AOI-машина» — это не offer, это capability/proof.

### Структура offer

Каждый offer:
- `id` — kebab-case slug.
- `name` — короткое название.
- `description` — 1–2 предложения.
- `category` — опциональная категория оффера (или null).
- `priority` — `primary` (основное предложение), `secondary` (дополнительное),
  `supporting` (поддерживающее/сопутствующее).

### Как определить priority

`primary` — основное предложение компании, ради которого клиент приходит.
`secondary` — важное дополнительное предложение, которое часто продаётся вместе
с primary или может быть точкой входа для другой аудитории.
`supporting` — сопутствующее предложение, которое редко покупают отдельно.

Если из входа неясно — используй `null` и создай DATA_GAP. Не выбирай `primary`
только потому, что offer единственный или кажется основным. Если priority
логически выведен, а не назван прямо, добавь meaningful decision с
`source_type=SOURCE_INFERRED`.

Если input сообщает только название offer, его `description` должен быть `null`.
Не сочиняй generic description.

## 3. Audience extraction

### Audience = операционный сегмент

Не изобретай искусственные marketing personas вида «Иван, 38 лет, руководитель
отдела закупок, живёт в Москве, любит кофе».

Если input не содержит персонализированных портретов — описывай сегмент
операционно:
- кто они (роль, должность, тип компании);
- что им нужно;
- какие проблемы решают;
- по каким критериям выбирают.

### Структура audience

Каждая аудитория:
- `id` — kebab-case slug.
- `segment` — короткое название сегмента.
- `description` — 1–2 предложения, кто они.
- `needs[]` — что им нужно.
- `problems[]` — какие проблемы решают.
- `selection_criteria[]` — по каким критериям выбирают подрядчика/продукт.

Если `needs`, `problems`, `selection_criteria` неизвестны — пустые массивы `[]`.

Если известен только `segment`, `description` должен быть `null`, а не
пересказом названия сегмента.

### Когда audiences[] может быть пустым

Если input вообще не упоминает аудиторию и не даёт оснований для inference —
`audiences[]` может быть пустым массивом, и это нормально. Зафиксируй DATA_GAP
в `data_gaps[]` с area=audience, impact=important.

## 4. Demand situation extraction

### Demand situation = trigger + job

Это особенно важная сущность для AI-first сайта.

**trigger** — что произошло / почему возник спрос сейчас.
Примеры триггеров:
- «запускаем новый электронный продукт»
- «текущий подрядчик не справляется с объёмами»
- «нужно быстро адаптировать баннер под 10 форматов»
- «хотим обновить интерьер дома»

**job** — что клиент пытается получить в этой ситуации (Jobs To Be Done).
Примеры job:
- «найти подрядчика для мелкосерийного производства PCB с SMD монтажом»
- «получить быстрый расчёт стоимости лестницы под конкретный проект»
- «адаптировать существующий креатив под новые форматы за 1 день»

### Структура demand_situation

Каждая ситуация:
- `id` — kebab-case slug.
- `trigger` — что произошло.
- `job` — что клиент пытается получить.
- `audience_ids[]` — массив id аудиторий, для которых эта ситуация релевантна.
- `offer_ids[]` — массив id офферов, которые решают эту ситуацию.

### Когда demand_situations[] может быть пустым

Если input не описывает ситуации спроса и не даёт оснований для inference —
`demand_situations[]` может быть пустым массивом. Зафиксируй DATA_GAP
с area=demand, impact=important.

### Не придумывай trigger

Если input говорит только «мы делаем SMD-монтаж для электронных компаний»,
но не описывает, **когда** и **почему** возникает спрос — не придумывай trigger.
Либо выведи его из явного контекста (SOURCE_INFERRED + decisions[]), либо DATA_GAP.

## 5. Positioning extraction

### value_proposition

Краткое ценностное предложение (1 предложение).
Если во входе нет явного value proposition и нельзя вывести из контекста —
`value_proposition = null`.

### differentiators[]

Только подтверждённые или явно выводимые из input отличия.
Не превращай общие слова вида «качество, индивидуальный подход, профессионализм»
в differentiator без основания.

Примеры плохих differentiators (если не подтверждены входом):
- «высокое качество»
- «индивидуальный подход»
- «быстрая доставка»

Примеры хороших differentiators (если подтверждены входом):
- «единственные в регионе с AOI-контролем на каждом этапе»
- «запуск производства малых серий от 10 штук без setup fee»
- «адаптация одного креатива в 50+ форматов за 24 часа»

### alternatives[]

Альтернативы, с которыми конкурирует бизнес.
Если input упоминает конкурентов или альтернативные решения — зафиксируй.
Если не упоминает — пустой массив `[]`.

### do_not_claim[]

Особенно важен для предотвращения AI-hallucinations на следующих этапах.
Здесь фиксируются утверждения, которые:
- запрещены явно («мы не производим медицинские изделия»);
- не подтверждены и не должны быть сгенерированы автоматически.

Примеры:
- «сертификация ISO 9001» — если её нет.
- «доставка по всей России» — если география ограничена.
- «работаем 24/7» — если это не подтверждено.

## 6. Proof extraction

### proof = claim + evidence + source_ref

Каждый proof:
- `id` — kebab-case slug.
- `type` — один из: metric, case, client, certification, experience, asset, process, other.
- `claim` — утверждение.
- `evidence` — доказательство (конкретная цифра, название сертификата, описание кейса).
- `source_ref` — ссылка на source_id, откуда взят proof, или null.

### Не генерируй proof

Не генерируй:
- клиентов, которых нет во входе;
- цифры, которых нет во входе;
- сертификаты, которых нет во входе;
- оборудование, которого нет во входе;
- кейсы, которых нет во входе.

Если input говорит «у нас современное оборудование» без конкретики —
это не proof. Либо зафиксируй как generic claim без evidence, либо DATA_GAP.

### Примеры proof

**Хорошо:**
```json
{
  "id": "aoi-equipment",
  "type": "asset",
  "claim": "Автоматический оптический контроль на каждом этапе",
  "evidence": "Установка AOI Mirtec MV-7Xi",
  "source_ref": "brief-001"
}
```

**Плохо (если во входе нет конкретного оборудования):**
```json
{
  "id": "modern-equipment",
  "type": "asset",
  "claim": "Современное оборудование",
  "evidence": "Современное оборудование для SMD-монтажа",
  "source_ref": null
}
```

Второй пример не содержит доказательства, только повторяет claim.

## 7. Objections extraction

### objection = возражение клиента

Если input упоминает типичные возражения, опасения, барьеры клиентов —
зафиксируй их.

### supported_response

Если у возражения есть доказанный ответ во входе — зафиксируй.
Если доказанного ответа нет — `supported_response = null`.

Не придумывай rebuttal.

### Примеры

**Хорошо (есть доказанный ответ):**
```json
{
  "id": "minimum-order",
  "objection": "Боимся, что минимальная партия слишком большая для нас",
  "supported_response": "Запускаем производство от 10 штук без setup fee"
}
```

**Хорошо (нет доказанного ответа):**
```json
{
  "id": "price-concern",
  "objection": "Цена может быть выше, чем у конкурентов",
  "supported_response": null
}
```

## 8. Conversion extraction

### primary_goal

Главная цель конверсии (1 предложение).
Что должен сделать посетитель сайта.

Примеры:
- «запросить расчёт стоимости»
- «записаться на консультацию»
- «загрузить файлы проекта для оценки»
- «начать использовать инструмент»

Если неясно — `primary_goal = null`.

### primary_cta

Главный call-to-action:
- `label` — текст кнопки.
- `action` — описание действия.

Если неясно — `primary_cta = null`.

### secondary_ctas[]

Дополнительные CTA.
Массив объектов {label, action}.

### contact_methods[]

Способы связи, упомянутые во входе.
Примеры: «телефон», «email», «Telegram», «форма обратной связи», «WhatsApp».

Не придумывай конкретные номера/адреса, если их нет во входе.

## 9. Content extraction

### required_messages[]

Смысл, который нельзя потерять при построении сайта.
Это не копирайтинг страницы, а ключевые маркетинговые сообщения.

Примеры:
- «Запускаем производство малых серий без минимальной партии»
- «Адаптируем один креатив в 50+ форматов за 24 часа»
- «Проектируем лестницу под конкретный интерьер, а не по каталогу»

### required_terms[]

Специфичная терминология бизнеса, которую нужно использовать точно.

Примеры:
- «SMD-монтаж»
- «AOI-контроль»
- «THT-компоненты»
- «performance-маркетинг»
- «интерьерная лестница»

### forbidden_messages[]

Сообщения, которые запрещены или не подтверждены и не должны появляться на сайте.

Примеры:
- «Мы — лучшие в России» (если не подтверждено)
- «Работаем со всеми отраслями» (если есть ограничения)
- «Гарантируем результат» (если гарантия не определена)

### faq_candidates[]

Вопросы и ответы, которые встречаются во входе или явно вытекают из контекста.

Каждый FAQ:
- `question` — вопрос.
- `answer` — ответ или null, если ответа нет.

Не генерируй общие FAQ вида «Сколько стоит?» или «Как заказать?», если они
не упомянуты во входе.

## 10. Brand extraction

### desired_character[]

Желаемые характеристики визуального характера, если упомянуты во входе.

Примеры: «technical», «approachable», «premium», «bold», «minimal».

Если не упомянуты — пустой массив `[]`.

### tone[]

Тон коммуникации, если упомянут во входе.

Примеры: «professional», «friendly», «direct», «conversational».

Если не упомянут — пустой массив `[]`.

### avoid[]

Явно нежелательные визуальные или коммуникационные характеристики.

Примеры: «playful», «corporate», «aggressive».

Если не упомянуты — пустой массив `[]`.

### constraints[]

Ограничения бренда, включая обязательные правила.

Примеры: «использовать только фирменный синий», «избегать красного цвета».

Если не упомянуты — пустой массив `[]`.

### existing_colors[], existing_fonts[]

Существующие фирменные цвета и шрифты, если упомянуты во входе.

Формат цветов — как есть во входе (название, HEX, RGB — без нормализации).
Формат шрифтов — название шрифта как есть.

Если не упомянуты — пустые массивы `[]`.

### reference

Визуальный референс, если упомянут во входе (URL или описание).
Если не упомянут — `reference = null`.

### Не выводи дизайн автоматически

Не используй автоматические правила вида:
- B2B → строгий
- technology → квадратный
- premium → чёрный
- friendly → rounded

Business category не определяет дизайн сама по себе.

## 11. Constraints extraction

### Пять категорий

- `legal[]` — юридические ограничения.
- `commercial[]` — коммерческие ограничения.
- `geographic[]` — географические ограничения.
- `technical[]` — технические ограничения.
- `content[]` — контентные ограничения.

Примеры:
- legal: «не можем работать с медицинскими изделиями без сертификации»
- commercial: «минимальный заказ от 10 штук»
- geographic: «работаем только в Московской области»
- technical: «не поддерживаем BGM-компоненты»
- content: «не упоминать конкретных клиентов без согласия»

Только реально известные ограничения.
Если ограничений нет — пустые массивы `[]`.

## 12. Semantic identity extraction

### Компактное AI-first представление

`semantic_identity` — это компактное AI-first представление сущности для:
- AI retrieval
- page semantics
- metadata
- future structured data
- consistency of terminology

Здесь допустима нормализация терминов, но НЕ добавление новых фактов.

Этот объект может частично повторять другие sections намеренно, но только
как компактная canonical semantic summary.

### Структура

- `primary_entity` — название сущности (если есть) или entity_type.
- `entity_type` — нормализованный тип (повтор из business.entity_type).
- `categories[]` — рыночные категории.
- `services_or_products[]` — нормализованный список услуг/продуктов.
- `audiences[]` — нормализованный список аудиторий.
- `use_cases[]` — нормализованный список use case.
- `locations[]` — нормализованный список локаций.

Все массивы — компактные, без длинных описаний.

### Примеры

```json
{
  "primary_entity": "SMD Service",
  "entity_type": "contract electronics manufacturer",
  "categories": ["SMD PCB assembly", "electronic manufacturing services"],
  "services_or_products": ["SMD assembly", "THT assembly", "PCB prototyping"],
  "audiences": ["electronics companies", "hardware startups"],
  "use_cases": ["small-batch PCB production", "prototype assembly"],
  "locations": ["Moscow region"]
}
```

## 13. Inference handling

### Когда inference допустим

Inference допустим, если:
1. Значение можно логически вывести из нескольких явных данных.
2. Вывод не добавляет новых бизнес-фактов, а нормализует/обобщает существующие.

### Примеры допустимого inference

**Хорошо:**
- Input: «Мы производим печатные платы для электронных компаний. Наши клиенты —
  стартапы, которые запускают новые продукты.»
- Inference: `business.category = "SMD PCB assembly"` (если это следует из контекста).
- Decision: `SOURCE_INFERRED`, evidence: «производство печатных плат для электронных компаний»,
  reason: «нормализация category из описания деятельности».

**Плохо:**
- Input: «Мы производим печатные платы.»
- Inference: `business.category = "SMD PCB assembly"` (нет оснований для уточнения до SMD).
- Правильно: `business.category = "PCB manufacturing"` или DATA_GAP.

### Когда фиксировать в decisions[]

Фиксируй в `decisions[]` только meaningful inference, который:
- меняет смысл или добавляет неочевидную интерпретацию;
- выводится из нескольких sources;
- может быть не очевиден для человека при ревью.

Не фиксируй тривиальные нормализации:
- kebab-case slug из названия;
- singular/plural нормализация;
- пунктуация и капитализация.

## 14. Conflict handling

### Когда sources противоречат друг другу

Если sources[] противоречат друг другу:
1. Не выбирай молча одно значение.
2. Зафиксируй конфликт в `data_gaps[]` с описанием противоречия.
3. Если более authoritative source можно установить только из явного контекста
   sources[] (например, `source_type=brief` против `source_type=notes`) —
   используй его и запиши `decision` с `source_type=SOURCE_EXPLICIT`.
4. Не выдумывай source authority. Если приоритет неясен — DATA_GAP.

### Примеры

**Хорошо (authority явно указана в metadata):**
- source_1 (type=notes, title=«Утверждённые изменения от собственника 12.09.2026»): «Минимальная партия 50 штук»
- source_2 (type=brief, title=«Старый бриф 2025»): «Минимальная партия 10 штук»
- Решение: использовать source_1, зафиксировать в decisions[]:
  - field_path: `constraints.commercial[0]`
  - source_type: `SOURCE_EXPLICIT`
  - evidence: «утверждённые изменения от собственника указывают минимальную партию 50 штук»
  - reason: «title явно маркирует source_1 как утверждённый и актуальный, а source_2 как старый»

`source_type` сам по себе authority не определяет. Нельзя автоматически считать
`brief` выше `notes` или наоборот.

**Плохо (authoritative source не определён):**
- source_1 (type=text): «Минимальная партия 50 штук»
- source_2 (type=text): «Минимальная партия 10 штук»
- Решение: НЕ выбирать молча. Зафиксировать DATA_GAP:
  - area: `constraint`
  - missing: «Минимальная партия: источники противоречат (50 vs 10)»
  - impact: `important`
  - question: «Какая минимальная партия: 50 или 10 штук?»

## 15. Data gap classification

### Три уровня impact

- `critical` — блокирует следующий этап (SiteModel не может быть построен).
- `important` — снижает качество (SiteModel может быть построен, но неполный).
- `minor` — желательно, но не критично.

### Примеры critical gaps

- Невозможно определить `business.entity_type` И `offers[0].name` одновременно.
- Полностью отсутствует информация о том, что компания делает.

### Примеры important gaps

- Отсутствует `positioning.value_proposition`.
- Отсутствуют `audiences[]`.
- Отсутствуют `demand_situations[]`.
- Отсутствуют `proof[]`.

### Примеры minor gaps

- Отсутствует `brand.desired_character[]`.
- Отсутствует `conversion.primary_cta`.
- Отсутствуют `content.faq_candidates[]`.

### question

Для каждого gap желательно сформулировать короткий вопрос к человеку.
Если вопрос сформулировать невозможно (слишком общий gap) — `question = null`.

Примеры хороших вопросов:
- «Какая минимальная партия для заказа?»
- «Какие существующие фирменные цвета использовать?»
- «Какое главное действие должен совершить посетитель сайта?»

Примеры плохих вопросов (слишком общие):
- «Расскажите о своих клиентах»
- «Опишите свой бизнес»

## 16. Edge cases

### Input полностью пустой

Если `sources[]` пустой или все `content` пустые — вернуть error:
«Невозможно построить SiteContext без входных данных».

### Input содержит только название

Если input содержит только название компании без описания деятельности —
попытаться определить хотя бы `business.name` и `context_id`, но зафиксировать
critical DATA_GAP для `business.entity_type` и `offers[]`.

### Input содержит только offer без business

Если input содержит только описание offer без упоминания компании —
построить `offers[]`, оставив неизвестные `business.entity_type`,
`business.category`, `business.summary` и `semantic_identity.entity_type`/
`primary_entity` равными `null`, и зафиксировать соответствующие DATA_GAP.

Если input содержит только название offer, оставить `offers[0].description = null`
и `offers[0].priority = null` с соответствующими DATA_GAP.

### Input противоречив по всем полям

Если все поля противоречивы и authoritative source не определён —
вернуть максимально пустой SiteContext с массивом `data_gaps[]`, описывающим
все конфликты.

## 17. Quality checks before return

Перед возвратом SiteContext проверь:

1. Все required поля присутствуют.
2. Все id — kebab-case slugs.
3. Все enum — валидные значения.
4. Неизвестные nullable-поля содержат `null`, а не пустые строки или догадки.
5. Нет дублирующихся id в offers[], audiences[], demand_situations[], proof[], objections[], data_gaps[].
6. Нет новых top-level полей вне schema.
7. Все audience_ids и offer_ids в demand_situations[] ссылаются на существующие id.
8. decisions[] содержит только meaningful inference, не тривиальные нормализации.
9. data_gaps[] содержит все critical/important gaps.
10. do_not_claim[] содержит утверждения, которые не должны быть сгенерированы автоматически.
11. Каждое meaningful inference (включая category, entity_type, value proposition и offer priority) имеет `SOURCE_INFERRED` decision.
