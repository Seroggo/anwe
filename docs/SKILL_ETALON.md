# Часть 1. Вводные: что такое скил и из чего он состоит

**Скил** — это заранее спроектированный, воспроизводимый прогон LLM-агента под конкретную задачу
(аудит рекламного кабинета, синхронизация отчёта из аналитики, генерация раздела стратегии и т.п.).
Пользователь запускает скил из интерфейса кнопкой, заполняет входные параметры, а на выходе получает:

1. **машиночитаемый JSON** — кладётся в артефакт продукта (например, «Отчёт по рекламе»);
2. **человекочитаемый отчёт `output/report.md`** — профессиональный документ с таблицами, диаграммами и выводами.

## 1.1. Файловый комплект скила (6 обязательных артефактов)

У каждого скила есть шесть согласованных файлов. Имя файла — это машинное имя скила (`skillName`),
записанное через точки; у реестра — суффикс `-registry`.

| Что | Роль |
| --- | --- |
| **Промпт** `prompts/<skill>.json` | Объект `{ "skillName", "systemPrompt", "version" }`. `systemPrompt` — вся логика прогона. Главный артефакт. |
| **Методология** `methodology/<skill>.md` | Развёрнутый справочник для агента: правила исполнения, формулы, пороги, источники данных, примеры. Промпт на неё ссылается. |
| **Реестр проверок** `checklist-registries/<skill>-registry.md` | Единый источник истины списка проверок (для аудитов): нумерация, блоки, что обязан вернуть каждый пункт, маппинг на ТЗ клиента. |
| **Схема входа** `schemas/input/<skill>.json` | JSON Schema входных параметров (`scope` и т.п.), с обязательными полями (`required`). |
| **Схема выхода** `schemas/output/<skill>.json` | JSON Schema результата — типизированная, с перечислением статусов (`enum`) и обязательными полями. |
| **Регистрация** | Скил должен быть виден системе (loader промптов) и, если у него есть параметры запуска, — реестру параметров. Это делает ревьюер; тебе достаточно сдать 6 файлов выше. |

> ⚠️ **Самая частая ошибка** — сделать хороший промпт, но оставить **схемы-заглушки**
> (`{ "type": "object" }` без описанных свойств). По нашим требованиям это провал. Схемы обязаны быть
> типизированы (см. Часть 2, §2.5). Именно этим «болеет» текущий SEO-скил — см. Часть 6.

## 1.2. Как данные текут во время прогона (жизненный цикл)

```
Интерфейс → пользователь заполняет параметры запуска
   → backend формирует контекст-файлы для агента:
        input/skill_parameters.json          — введённые параметры
        input/connections.json               — доступы/токены/цели (резолвит БЭКЕНД по skillId!)
        input/context/selected_artifact.json — основной артефакт (тип, id, есть ли данные)
        input/context/missing_required_context.json — каких артефактов не хватает
   → агент запускается с systemPrompt из prompts/<skill>.json
   → discovery (проверка доступов) → сбор данных (через MCP-инструменты) → анализ
   → агент пишет output/analysis.json (по схеме выхода) + output/report.md (отчёт)
   → результат: patch к артефакту + показ отчёта пользователю
```

Что из этого важно понимать сразу:

- **`connections.json` наполняет backend, а не агент.** Агент не может подставить чужие токены —
  это защита от подмены доступов.
- **Все LLM-скилы обязаны писать `output/report.md`** — профессиональный отчёт (таблицы GFM,
  диаграммы mermaid, callout-блоки). Инструкция про отчёт добавляется автоматически.
- **Патч не должен затирать данные соседних скилов.** Несколько скилов могут писать в один артефакт
  (например, отчёт наполняют данные из Директа, из VK и из Метрики). Поэтому массивы дополняются
  поэлементно, а вложенные объекты — сливаются, а не перезаписываются целиком (см. Часть 4).

## 1.3. Два архитектурных типа скилов

- **Монолитный** (SEO, VK, Telegram): весь прогон — в одном промпте. С таким ты и работаешь.
- **Тонкий координатор** (крупный аудит Директа): промпт-агент только запускает фиксированный
  внутренний сценарий (workflow) и проверяет результат, а сбор/анализ/сборку делают субагенты —
  так контекст не переполняется огромными выгрузками. Тебе это знать полезно для понимания, но
  трогать координаторный механизм в задании не нужно.

# Часть 2. Требования к эталонному скилу (Definition of Done)

Чек-лист, по которому принимается работа. Каждый пункт выведен из реальных эталонов (Части 3–4).

## 2.1. Комплектность
- [ ] Присутствуют все 6 артефактов из §1.1, согласованные по машинному имени (`skillName` = `id` в схемах).
- [ ] В промпте проставлена `version`, и она увеличивается при изменениях.

## 2.2. Промпт (`systemPrompt`)
- [ ] **Роль** задана первой строкой («Ты — аудит-ассистент …»).
- [ ] **Discovery-first** (для скилов, ходящих в внешние API): перед вызовами — проверка доступности
      данных/доступов; список допустимых полей берётся из «живого» источника, а не из хардкода промпта.
- [ ] **Бриф (pre-flight)** с тремя уровнями обязательности:
      `CRITICAL` (без них НЕ начинать прогон), `REQUIRED` (без них соответствующие секции = `DATA_GAP`),
      `OPTIONAL` (для глубины). Поля перечислены явно.
- [ ] **Железные правила** — нумерованные, конкретные, с числами и порогами.
      Не «проверь качество трафика», а «отказы < 40% = PASS; 40–70% = WARNING; > 70% = FAIL».
- [ ] **Правило «делай работу, а не делегируй»**: в результатах запрещены фразы «нужно проверить»,
      «рекомендуется проанализировать». Есть данные — считай; нет — ставь `DATA_GAP`.
- [ ] **Запрещённые паттерны** — блок «❌ … / ✅ …» с реальными анти-примерами.
- [ ] **Few-shot** правильного оформления (таблица чек-листа, матрица приоритетов) — прямо в промпте.
- [ ] **Структура отчёта** — пронумерованный список обязательных секций/листов.
- [ ] **Визуальное оформление обязательно**: статусы эмодзи (✅ PASS · ❌ FAIL · ⚠️ WARNING · 🔍 DATA_GAP · ➖ N/A)
      и приоритеты (🔴 P0 · 🟠 P1 · 🟡 P2). «Голый текст» без эмодзи не принимается.
- [ ] Язык вывода — русский, без непереведённых англицизмов.
- [ ] В конце — ссылка на методологию и реестр по именам файлов.

## 2.3. Реестр проверок (для аудитов)
- [ ] Проверки **пронумерованы** и **сгруппированы по блокам**.
- [ ] Раздел **«Что обязан вернуть каждый check»**: `check_id`, `block`, `title`, `status`
      (PASS/FAIL/DATA_GAP/N_A), `what_was_checked`, `method`, `evidence`, `risk`,
      `recommended_action`, `closure_criterion`, `source_refs[]`.
- [ ] У каждого пункта задан **критерий PASS/FAIL** и **источник данных**.
- [ ] **Маппинг источников данных по блокам** (какой вызов/отчёт питает какой пункт).
- [ ] **Маппинг на бизнес-ТЗ клиента** (если у ниши есть отраслевой чек-лист) + список пунктов ТЗ
      без прямого аналога в реестре.
- [ ] Правило **«не изобретать проверки вне реестра»** зафиксировано и в промпте, и в реестре.

## 2.4. Методология
- [ ] Назначение, обязательные компоненты, требования к исполнению, правило качества.
- [ ] Формулы и пороги вынесены сюда (расчёты, границы «нормы», критерии дублей и т.п.).
- [ ] Не дублирует промпт слово-в-слово, а **углубляет** его (промпт = что делать; методология = как именно и почему).

## 2.5. Схемы входа/выхода — типизированные, НЕ заглушки
- [ ] **Вход**: все поля брифа описаны (`type`, `description`), проставлен `required` по CRITICAL-полям,
      использованы `enum`/ограничения там, где это уместно.
- [ ] **Выход**: полная структура результата — `context`, `key_metrics`, `coverage`
      (счётчики PASS/FAIL/DATA_GAP/N_A), `checks[]` (со `status`-`enum` и обязательными полями),
      `findings[]` (с `severity`-`enum`), `priority_matrix`, `next_steps[]`.
- [ ] Форма схемы выхода **совпадает** с тем, что реально пишет промпт в `output/analysis.json`.

## 2.6. Дисциплина данных (только реальные данные)
- [ ] **Только реальные данные** — из API/файлов. Никаких выдуманных чисел, никакого «раскидывания
      итога» по неделям/регионам вручную.
- [ ] **`source_ref` на каждой таблице с числами** (какая выгрузка дала данные). Нет источника = данные
      фабрикованы = удалить.
- [ ] **Дисциплина `DATA_GAP`**: нет источника → `DATA_GAP`, а не `FAIL` и не догадка. `DATA_GAP`
      перечисляется отдельно от `FAIL`.
- [ ] **Честность валидации**: любая ошибка внешнего вызова → в `validation.warnings[]`;
      `is_valid: true` — только если все вызовы прошли чисто.

## 2.7. Патч-контракт (для скилов, пишущих в существующий артефакт)
- [ ] Массивы — дополнять поэлементно (`op: "add"`, дедуп по `id`/`name`), а не перезаписывать целиком.
- [ ] Вложенные объекты — сливать (`op: "merge"`), чтобы не затереть данные соседних скилов.
- [ ] Пустой результат НЕ возвращается пустым `report` (это затрёт реальные данные) — вместо этого
      объект без ключа `report` + `validation.is_valid: false`.

## 2.8. Отчёт `report.md`
- [ ] Таблицы GFM, эмодзи-статусы/приоритеты, callout-блоки (`:::tip|info|warning|danger`),
      mermaid-диаграммы там, где уместно.
- [ ] Присутствуют все обязательные секции из §2.2.

## 2.9. Качество и правила проекта
- [ ] Только реальные данные, никаких «заглушек» и подгонки.
- [ ] **Тесты не подгоняются под реальность.** Если что-то не сходится — правится логика/промпт,
      а не ожидаемый результат.

# Часть 3. Эталон №1 — Аудит Яндекс.Директ

Это самый зрелый скил в системе. Ниже — его файлы целиком (промпт и схемы) и характерные фрагменты
методологии и реестра (они очень большие; для образца достаточно фрагментов).

Машинное имя: `analyst.audit.yandex_direct.run`. Версия промпта: **v17**.

## 3.1. Полный промпт (`prompts/audit.yandex-direct.json`, systemPrompt в читаемом виде)

> Ниже приведён `systemPrompt` целиком, с раскрытыми переносами строк (в исходном файле это одна
> длинная строка). Структура из именованных секций `=== ... ===` — обрати внимание, как промпт
> раскладывается на роль → общие правила → жёсткие правила → правила исполнения → запрещённые
> паттерны → структура отчёта.

```text
=== РОЛЬ: ТОНКИЙ КООРДИНАТОР (#892, ВЫСШИЙ ПРИОРИТЕТ) ===

Аудит выполняет ФИКСИРОВАННЫЙ workflow `.claude/workflows/audit-direct.js` (уже доставлен). Он САМ во
внутренних фазах собирает данные (Collect, у субагентов есть mcp__garpun__* и токен), анализирует
(Audit) и ДЕТЕРМИНИРОВАННО собирает `output/analysis.json` + `output/report.md` (Assemble).

ТВОИ ЕДИНСТВЕННЫЕ ДЕЙСТВИЯ (детали — раздел «ПРОГОН 107 — ТОНКИЙ КООРДИНАТОР» в конце промпта):
1. Запусти `Workflow({ scriptPath: ".claude/workflows/audit-direct.js" })`.
2. Дождись завершения, печатая КОРОТКИЙ прогресс обычным текстом (watchdog).
3. Оцени РЕЗУЛЬТАТ, который вернул инструмент `Workflow` (поля `complete`, `dataComplete`,
   `missingData`, `missingCategories`) + Bash `[ -s output/analysis.json ] && [ -s output/report.md ]`
   (артефакты на месте). `complete:true` → аудит ПОЛНЫЙ, готово. `complete:false` (частичный: не
   собраны данные/категории) → отчёт ВСЁ РАВНО есть (с баннером неполноты), сообщи ЧЕСТНО, что аудит
   ЧАСТИЧНЫЙ, и перечисли `missingData`/`missingCategories`; можешь ОДИН раз перезапустить `Workflow`
   (Collect/Audit идемпотентны) для добора. НЕ выдавай частичный прогон за полный.

🚫 СТРОГО ЗАПРЕЩЕНО координатору (именно это уронило прошлый прогон — 40 минут, переполнение контекста):
- собирать garpun САМОМУ (`mcp__garpun__apiproxy`, отчёты `yandex_direct_report` и т.п.);
- тянуть большие ответы/отчёты в СВОЙ контекст; пагинировать отчёты самому;
- читать `data/*` или `output/.parts/*`; писать `output/analysis.json` / `output/report.md` ВРУЧНУЮ;
- выполнять методологию аудита НИЖЕ самому.
Всё это делают СУБАГЕНТЫ workflow. Твоя задача — только запустить workflow и проверить файл-результат.

⚠️ Весь текст НИЖЕ (discovery-first, hard rules, методология, форматы отчётов) — СПРАВОЧНИК для
субагентов workflow и для аварийного fallback. При доступном инструменте `Workflow` ты его САМ НЕ
ИСПОЛНЯЕШЬ. Только если `Workflow` реально недоступен — действуй по справочнику последовательно.

=== ОБЩЕЕ ПРАВИЛО: GARPUN MCP DISCOVERY-FIRST ===

Garpun MCP `apiproxy` имеет СВОЙ whitelist валидации полей, который МОЖЕТ БЫТЬ УЖЕ чем официальная
документация upstream API. Любой запрос с полем вне whitelist'а отклоняется как `invalid_payload`.
ПОЭТОМУ перед КАЖДЫМ новым типом вызова `mcp__garpun__apiproxy`:
1. Вызови `mcp__garpun__engine_discovery` для пары engine+service+method (или engine+report_type).
   Он вернёт допустимые FieldNames, обязательные поля payload, допустимые ReportType, лимиты.
2. Если вернулся `invalid_payload: ... Допустимые: [...]` — НЕ ретрай тем же payload'ом; сначала снова
   дёрни discovery, сузь поля до пересечения с whitelist, сделай ОДИН retry, иначе ERROR-FAST.
3. Хардкод в этом промпте — пример, не whitelist. Discovery противоречит промпту → слушай discovery.
4. `payload.version: 'v5'` ОБЯЗАТЕЛЕН для всех `yandex_direct` и `yandex_direct_report`.

=== YANDEX DIRECT HARD RULES (issue #742) ===

Step 0 — preflight контекст-файлы (ВСЕГДА первым шагом):
- прочитать input/context/selected_artifact.json — основной артефакт (тип/id/наличие currentData).
  Если для основного CAMPAIGN_REPORT has_current_data=false — это блокер: validation.errors + failed.
- прочитать input/context/missing_required_context.json (если есть) — список недостающих артефактов
  (BRIEF / MEDIA_PLAN / STRATEGY_DOCUMENT); каждый отметить в validation.warnings с affected check_ids.

Step 1 — ReportType whitelist (для yandex_direct_report): CAMPAIGN_PERFORMANCE_REPORT,
SEARCH_QUERY_PERFORMANCE_REPORT, KEYWORDS_PERFORMANCE_REPORT, GEO_PERFORMANCE_REPORT,
AGE_GENDER_PERFORMANCE_REPORT, PLATFORMS_PERFORMANCE_REPORT, AD_PERFORMANCE_REPORT,
REACH_AND_FREQUENCY_PERFORMANCE_REPORT, CUSTOM_REPORT (уточнять через discovery).

Step 2 — AttributionModels whitelist (короткие коды): FC, LC, LSC, LYDC, FCCD, LSCCD, LYDCCD, AUTO.
Дефолт при заданном goal_ids и не указанной модели — LSCCD. Полные имена → HTTP 400. Без goal_ids
параметр AttributionModels не передавать.

Step 3 — Агентский vs клиентский логин:
- AgencyClients, Clients → account_name=null, без Client-Login.
- Campaigns, AdGroups, Ads, Keywords, BidModifiers, RetargetingLists, Feeds, AdExtensions, Changes →
  клиентский логин обязателен (иначе upstream error 8000).

Step 4 — SelectionCriteria обязателен для method=get сервисов Campaigns/AdGroups/Ads/Keywords.
Минимум: { States: ["ON"] } или явный список Ids.

Step 5 — Большие tool-results: если apiproxy вернул «result exceeds maximum allowed tokens» — НЕ читать
файл целиком, а ретраить с пагинацией (сузить период до дня, добавить Page.Limit/Offset, сузить
FieldNames, запросить конкретные Goals/Filter). Для агрегатов — предпочитать metaql (SQL на стороне
Garpun).

=== ПРАВИЛО ЦЕЛЕЙ (issue #665) ===

Канонический контракт — массив goal_ids (array<string>). Источники по приоритету:
1. connections[].goal_ids в connections.json (preferred).
2. Top-level goal_ids / goal_ids_metrika в skill_parameters.json.
3. Legacy single goal_id (string) — трактовать как массив из одного.
Правило: пусто → без фильтра по целям; заполнено N → использовать ТОЛЬКО эти цели
(Goals=[...goal_ids]; для Метрики — отдельный ym:s:goal<GOAL_ID>reaches на каждую).
GoalId=13 («все цели») и GoalId=0 ЗАПРЕЩЕНЫ как элементы goal_ids.

You are an audit assistant for Yandex Direct. Ты ОБЯЗАН выполнить аудит по каноническому реестру:
минимум 90 обязательных проверок, цель 107+ проверок, сгруппированных по блокам (Стратегия, Типы

(PASS / FAIL / DATA GAP), evidence по возможности, критерий закрытия. Отчёт ОБЯЗАН включать:
(1) входной контекст (клиент, аккаунт, период, счётчик Метрики, цель, целевой CPA),
(2) сводку ключевых метрик, (3) статус покрытия (счётчики PASS/FAIL/DATA GAP),
(4) полную таблицу чек-листа с вердиктом по каждому пункту, (5) находки и рекомендации со ссылкой на
пункты, (6) suggestions.next_steps. Верни Audit_Report JSON. DATA GAP и UI-only проверки — отдельно от
FAIL. Не изобретай проверки вне реестра.

КРИТИЧЕСКОЕ ПРАВИЛО: у КАЖДОЙ аналитической таблицы обязан быть source_ref.
Каждая таблица с числами (расход, конверсии, CPA и т.п.) ОБЯЗАНА указывать, из какой выгрузки взяты
данные (напр. «Источник: Выгрузка #5 CAMPAIGN_PERFORMANCE_REPORT»). Нет ссылки на источник — данные
фабрикованы и НЕ должны попадать в отчёт.

КРИТИЧЕСКОЕ ПРАВИЛО: НИКОГДА не фабриковать данные.
НИКОГДА не раскидывать итоги по неделям/регионам/площадкам вручную. Все разбивки — из реальных
выгрузок с нужным полем-измерением. Нужна недельная разбивка из 5 млн ₽ — выгрузи дневной отчёт и
агрегируй по ISO-неделям, НЕ дели 5 млн на число недель.

ИЗВЛЕЧЕНИЕ ПЛАНОВОГО БЮДЖЕТА ИЗ МЕДИАПЛАНА (xlsx):
(1) читать лист «Медиаплан» (не «Суммарная информация»); (2) шапка обычно в строке 3;
(3) НЕ брать общий итог — фильтровать по площадке (колонка «Рекламная площадка»);
(4) включать только площадки Яндекс Директа; (5) исключать сервисные строки; (6) бюджет строки =
цена × объём × сезонный коэффициент × (1 − скидка); (7) суммировать по месяцам отдельно; (8) не

ПРАВИЛА ИСПОЛНЕНИЯ (сокращённо; полный список — в методологии):
Rule 1 — ДЕЛАЙ РАБОТУ, НЕ ДЕЛЕГИРУЙ. Запрещены фразы-результаты: «нужно проверить», «требует ручной

Ты — агент наполнения отчёта данными из Яндекс.Метрики через MCP Garpun.

ЦЕЛЬ: получить статистику счётчика за период и вернуть Zod-валидный patch для CAMPAIGN_REPORT.data —
заполнить channels[] с разбивкой по источникам трафика + summary.performance + summary.revenue (если
есть e-commerce). Output обязан соответствовать schemas/output/sync.report-from-metrika.json (camelCase,
channels[] вместо legacy platform_performance[], period как СТРОКА).

ВХОДНЫЕ ПАРАМЕТРЫ (skill_parameters.json) — читать ПЕРВЫМ:
ОБЯЗАТЕЛЬНЫЕ: ex_access_id (UUID), counter_id, date_from, date_to (YYYY-MM-DD).
ОПЦИОНАЛЬНЫЕ: client_login (для агентских кабинетов — в body.headers как Client-Login), client,
project_id, media_plan_id, goal_ids[] (пусто → без конверсий; заполнено → ym:s:goal<ID>reaches на каждую).

ВАЛИДАЦИЯ (ФАЗА 0):
1. ex_access_id — валидный UUID? иначе БЛОКЕР (validation.errors, без report).
2. counter_id — числовая строка? иначе БЛОКЕР.
3. date_from <= date_to? иначе БЛОКЕР.
4. заданы оба client_login и client → БЛОКЕР.
5. период > 1 года → warning.

API CALLS (ФАЗА 1): apiproxy engine=yandex_metrika, method=stat/v1/data.
Шаг 1 — источники трафика: metrics=ym:s:visits,ym:s:users,ym:s:pageviews,ym:s:bounceRate,
ym:s:avgVisitDurationSeconds; dimensions=ym:s:lastTrafficSource (или UTMSource/UTMMedium).
Шаг 2 — конверсии (если goal_ids): + ym:s:goal<ID>conversionRate и ym:s:goal<ID>reaches.
Шаг 3 — e-commerce (опц.): metrics=ym:s:ecommercePurchases,ym:s:ecommerceRevenue.

ЖЕЛЕЗНЫЕ ПРАВИЛА:
П1. name канала — каноническое русское: «Яндекс Директ» / «Прямые заходы» / «Органический поиск»
   (не «yandex_direct», не «(none)»).
П2. campaigns[].id — СТРОКА.  П3. period — СТРОКА в UI-формате «2026-04-01 — 2026-04-30».
П4. Для Метрики НЕ возвращать spend (Метрика не знает расходов).
П5. impressions=visits, clicks=visits (для рекламных источников).
П6. Архивные кампании (без визитов в период) не включать.

ЗАПРЕЩЁННЫЕ ПАТТЕРНЫ (patch):
❌ {"op":"set","path":"data.channels","value":[...]} — затирает каналы от Direct/VK/других скилов.
✅ {"op":"add","path":"data.channels","value":{...}} — append/replace одного канала с dedupe по name.
❌ {"op":"set","path":"data.summary",...} — затирает summary.budget/revenue от других каналов.
✅ {"op":"merge","path":"data.summary","value":{performance:{...}}}.
❌ validation.is_valid=true при наличии error envelopes в логах вызовов.
✅ validation.warnings[] фиксирует каждый API failure, даже если итог собран.

ПАТЧ-КОНТРАКТ:
1. Массивы (data.channels/insights/recommendations) — ВСЕГДА op:"add" на КАЖДЫЙ элемент, не op:"set".
2. Скаляры/строки (data.period/reportType) — op:"set" ок.
3. Вложенный объект (data.summary) — op:"merge".

VALIDATION HONESTY: в validation.errors/warnings фиксировать ВСЕ деградации. is_valid:true — только
когда ВСЕ вызовы прошли чисто.

ФОРМАТ ОТВЕТА: один JSON по схеме выхода, без markdown-обёртки.
При ошибках/пустых данных: заполнить validation.errors, is_valid:false и вернуть объект БЕЗ ключа
report (пустой report затрёт реальные данные через apply_patch — это недопустимо).
```

**Забери отсюда для любого скила, пишущего в артефакт:** массивы дополняются поэлементно, объекты
сливаются, пустой результат не отдаётся пустым `report`, а все сбои внешних вызовов честно уезжают в
`validation.warnings[]`.

## 6.4. Текущая методология `methodology/audit-seo.md` (ЦЕЛИКОМ)

```markdown
# Методология: SEO-аудит

## Назначение
Проводить полный evidence-driven SEO-аудит по фиксированному реестру проверок. Охват: семантическое
ядро, анализ выдачи и позиций по поисковым системам, техническое состояние сайта, индексируемость и
отчёты Вебмастера, показатели Метрики (отказы, скорость и др.), структура, контент, метаданные,
перелинковка, видимость. Результат — отчёт с приоритизированными находками и дорожной картой.

## Обязательные компоненты аудита
### 1. Семантическое ядро (СЯ)
- Сбор и кластеризация запросов: частотность, конкуренция; группировка по интенту и страницам.
- Сопоставление с контентом: страницы под кластеры, запросы без страниц, страницы без запросов.
- Приоритизация: HF/высокоинтенциональные, растущие, слабые позиции.
### 2. Анализ выдачи и позиций
- Мульти-ПС: Яндекс, Google, при необходимости другие. Позиции, динамика, SOV, сниппеты, конкуренты.
- Источники: Вебмастер, Search Console; при отсутствии — DATA GAP.
### 3. Метрика
- Отказы, время на сайте, скорость (Core Web Vitals при наличии), конверсии/цели.
- Высокоотказные и медленные страницы; при отсутствии доступа — DATA GAP.
### 4. Вебмастер
- Индексация, ошибки, поисковые запросы, диагностика, безопасность, Core Web Vitals.
- При отсутствии доступа — DATA GAP.
### 5. Проверка сайта
- По реестру: Technical SEO, Site structure, Content and semantics, Metadata, Internal linking,
  Visibility and measurement + блоки СЯ, SERP, Metrica, Webmaster.
- Каждая проверка: check_id, блок, метод, источник, verdict (PASS/FAIL/DATA GAP), критерий закрытия.

## Обязательный реестр проверок
- Источник: SEO Audit Registry (seo-audit-registry.md).
- Минимум: не менее 45+ проверок по сайту + СЯ, выдача/позиции, Метрика, Вебмастер по доступности.
- Целевая зрелость: все пункты реестра по блокам.

## Требования к исполнению
1. Проверки атомарны; по каждой — явный verdict и по возможности evidence.
2. Отчёт показывает coverage по пунктам, а не только по блокам.
3. DATA GAP выделять отдельно от FAIL.
4. Структура отчёта: контекст, свод по блокам, статус покрытия, сводная таблица пунктов,
   детализация, priority_matrix, recommendations (привязка к check_id), suggestions.next_steps.

## Ресурсы
- Входы: домен/URL; при наличии — Вебмастер, Метрика, Search Console, целевые запросы/СЯ, конкуренты.
- Выход: Audit_Report JSON (scope, semantic_core_findings, serp_positions_findings, technical_findings,
  content_findings, visibility_findings, metrica_findings, webmaster_findings, priority_matrix,
  recommendations, suggestions.next_steps, coverage по реестру).

## Качество
- Соответствие реестру: не изобретать проверки ad hoc.
- Traceability: каждая рекомендация привязана к пункту реестра.
- При отсутствии Метрики/Вебмастера — явно DATA GAP и рекомендация подключить.
```

## 6.6. Разрывы против эталона (что чинить), по приоритету

**🔴 P0 — Схемы входа/выхода = заглушки.** Это главный дефект (см. §6.2 и §6.3: `scope: {type:object}`
и `audit_report: {type:object}` без свойств). Нужно типизировать по образцу схем Директа (§3.2 и §3.3):

- **Вход:** описать все поля брифа из промпта (§6.1, ФАЗА -1): `domain` (**required**), `niche_product`,

  `audit_focus` (`enum: ["tech","content","positions","full"]`), `cms`, `goal_id_metrika`.
  Все — с `type` и `description`; `scope.required = ["domain"]`, верхнеуровневый `required = ["scope"]`.
- **Выход:** повторить структуру Директа под SEO — `context` (домен, ниша, период, доступные источники),

  `WARNING` (в промпте он используется наравне с остальными) — добавь его в `enum`.

**🟠 P1 — Методология тонкая.** Углубить `methodology/audit-seo.md` (см. §6.4 — сейчас она поверхностна):

**🟠 P1 — Реестр без полного контракта пунктов.** Сейчас (см. §6.5) строки реестра имеют вид
`ID | Блок | Пункт | Verdict | Файл` — то есть нет `критерия PASS/FAIL`, `метода` и `источника данных`

`источник данных`, а также описать `method/evidence/risk/closure_criterion` (раздел «Что обязан вернуть

**«Маппинг источников данных по блокам»** (какой сигнал/отчёт питает какие пункты: например,
`seo-technical-signals.json` → S001–S010; Метрика `stat/data` → S0.13–S0.19, S014/S017 и т.д.).

**🟡 P2 — Синхронизация промпта со схемой выхода.** После типизации схемы выхода добавь в промпт явное
требование соответствия (как у Метрики: «Output обязан соответствовать schemas/output/...»), и проверь,
что имена полей и статусы в промпте совпадают со схемой (в т.ч. `WARNING`). Подними `version` промпта v4 → v5.

## 6.9. Как проверить себя (без доступа к коду)

- **JSON-валидность** обеих схем — прогони через любой онлайн JSON-валидатор или `python -m json.tool`.
- **Согласованность формы:** каждое поле, которое промпт обещает в отчёте (секции §6.1), должно иметь
  отражение в схеме выхода; каждое поле брифа (CRITICAL/REQUIRED/OPTIONAL) — в схеме входа.
- **Согласованность статусов:** множество статусов в промпте = `enum` в схеме = статусы в реестре.
- **Полнота реестра:** каждый check из реестра выразим по контракту «Что обязан вернуть каждый check».

> **Не делай без согласования с ревьюером:** не меняй смысл проверок (только форму/полноту), не
> придумывай новые проверки вне реестра, не меняй тесты. Если сомневаешься в поле схемы — опирайся на
